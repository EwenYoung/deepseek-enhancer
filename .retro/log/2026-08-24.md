## s1 元素级 CSS 变量声明优先于继承——html 内联覆盖对它无效

- 症状：applyOpacity 把 `--panel-bg` 写在 `document.documentElement.style` 上，滑杆拖动面板毫无反应；直觉以为"内联样式 > 样式表"应该生效。
- 原因：ink 主题把变量声明在**面板元素自身**；CSS 自定义属性按「元素上匹配的声明（任意优先级）> 从父级继承的值」解析。
- 解法：不要在主题块里声明最终合成变量再用祖先内联覆盖；把可变部分拆成独立低层变量（本例 `--panel-alpha`），主题块内写 `rgba(底色, var(--panel-alpha, 原值))`，JS 只写低层变量。四种主题分支全部自动跟随。

## s2 ink 深色主题下 --accent/--danger 是浅色，按钮文字必须用 --accent-text

- 症状：深色模式下"确认恢复"按钮文字不可见（白字落在浅灰 `--accent: #e4e4e7` 上，对比度 1.27:1）；ink 主题改造批量改色时漏改写死 `color:#fff` 的按钮。
- 原因：ink 深色把 accent 系从深色反转为浅色，但文字色没跟着换；危险态同理（深色 `--danger: #f87171` 也是浅色）。
- 解法：凡 `background: var(--accent)` 或 `var(--danger)` 的按钮，文字一律 `color: var(--accent-text,#fff)`（两模式均 ≥4.5:1）；排查手段 grep `color:\s*#fff` + 按 WCAG 公式算对比度。

## s3 官方新组件的主题冲突：元素级变量不走 dsw-alias 链，当前会话行 * 涂装会污染行内元素

- 症状：官方侧边栏多选复选框选中色永远是 DeepSeek 蓝，body 级覆盖 `--dsw-alias-brand-primary` 无效；主题化后勾选当前会话行时圆点内露出方形色块。
- 原因：官方组件把 `--dsl-checkbox-color` 声明在**复选框元素自身**（不消费 dsw-alias 变量链）；主题的 `a[data-ds-sidebar-selected] *` 规则给当前会话行所有子元素（含对勾所在 14x14 方形 svg）刷 `sidebarHighlight` 背景。
- 解法：同级选择器覆盖 + `!important`（特异性算清楚：`*` 贡献 0、`:has()` 按参数计）；覆盖含整个圆点子树；对勾前景按品牌亮度取色（`textColorOnBrand`）；排查图形异常先 svg 栅格化。

## s4 特异性三列公式：:first-child 等伪类归第二列，不是第三列

- 症状：注释里写 `(1,3,1)`，实际应是 `(1,4,0)`——把 `:first-child` 算成了伪元素（第三列），被 review 抓出；功能上仍满足需求但误导维护者。
- 原因：CSS 特异性三列是 `(id, 类/属性/伪类, 元素/伪元素)`；伪类（`:hover`、`:first-child`、`:last-child`、`:not(...)` 参数按冲突列计，`:not`/`:is` 本身不计）全归第二列；只有伪元素（`::before`/`::after`）和标签选择器归第三列。
- 解法：写进注释的特异性数字先按公式逐列核算再写；与 `*` 贡献 0、`:has()` 按参数计统一使用同一套核对流程。

## s5 storage 读出的配置可能是 undefined / {} / 部分字段，读取侧必须合并默认值

- 症状：① `getConfig` 用 `(存储值) || 默认值`，备份 round-trip 写入 `{}` 后返回全 undefined 字段对象（主题名显示 "undefined"、themeIdx 算出 NaN）；② 导入旧格式备份时"先 clear() 再只写备份里存在的键"把新键静默清空。
- 原因：`||` 只防 undefined 不防 `{}`（空对象是真值）；全量替换语义下"缺键=丢弃"与"缺键=默认值"不等价。
- 解法：读取侧 `{ ...DEFAULT_CONFIG, ...存储值 }` 合并；导入侧 `Object.hasOwn(data, key) ? data[key] : BACKUP_KEYS[key]` 回填。给 BACKUP_KEYS 新增键时两条路径自动安全。

## s7 官方多选模式没有独立入口：入口在会话行三点菜单「多选」，退出在顶部栏无文字图标按钮

- 症状：自动化找不到官方「多选」的入口与退出路径——没有独立按钮，无法用 title/文案定位。

## s8 自动化搞坏页面状态后，先查草稿再 reload 兜底

- 症状：自动化操作后侧边栏会话列表清空/状态异常，继续探测全部失真。
- 原因：合成 click 官方 React 控件会触发真实状态变更（如多选退出后列表清空），页面进入异常态后 DOM 探测结果不可信。
- 解法：先查输入框有无草稿（`document.querySelector('textarea').value`），无草稿直接 `location.reload()`，扩展与主题会自动重新注入；自动化守则：绝不碰「删除」类按钮；每步操作后断言页面预期状态再继续。

## s9 助手回复导出是双数据源：缓存只覆盖本页会话，历史会话必须走已渲染 DOM

- 症状：HTML 导出里助手回复的 markdown 全部原样文本（无标题/粗体/代码块），正文混着「css复制下载」按钮文字和「-1」引用角标；同一功能在「刚生成完回复就导出」时正常。
- 原因：`scrapeMessages` 优先读 `#ds-mini-asst-raw` 缓存的原始 markdown，但该缓存由 SSE 拦截写入，只覆盖当前页面会话中实时生成的回复；历史会话回退到 `replyEl.textContent`——markdown 语法已丢失且混入工具栏按钮、引用角标文字。
- 解法：历史路径不用 `textContent`，用 `extractRenderedReplyHTML`：克隆 `.ds-assistant-message-main-content` → 删装饰 → `sanitizeRenderedHTML` 白名单净化 → 作为 `renderedHTML` 直接进气泡。判断路径：消息上有无 `renderedHTML` 字段。

## s11 布局验证必须断言计算样式与几何，DOM 顺序不代表视觉

- 症状：微信风格导出里用户气泡没靠右（漏 `.wx-me{justify-content:flex-end}`），但 agent 自验「通过」——当时只检查了头像在 DOM 里的相对位置；用户人工验证才发现。
- 原因：flex 行内元素默认从行首排布，DOM 顺序（气泡在头像前）与视觉方位（气泡是否贴右缘）是两回事；「元素存在且顺序对」推不出「对齐对」。
- 解法：对布局结论至少断言二者之一：`getComputedStyle(row).justifyContent` 等对齐属性；或几何——子项右边缘与容器右边缘重合（`Math.abs(a.right - row.right) < 1`）。截图若工具链拿不到更不能当成已验证。

## s12 用户报障先读真实产物（导出文件/页面实测）再动代码

- 症状：用户报障（如微信风格导出气泡不靠右、历史会话 markdown 原样文本）后，agent 凭代码印象或自己「自验通过」的结论推断开改，绕了一圈才发现现象与真实产物不符。
- 原因：内存里的代码印象 ≠ 真实产物；「自验通过」不等于「用户看到的导出文件/页面正确」——问题可能出在验证方法或数据源，没看产物前无法区分。
- 解法：接到报障先打开真实产物定位现象（导出的文件内容、真实页面实测）再回代码改，不要先改代码再等用户复验；用户报障指向的真实产物就是最高优先级验收标准。

## s13 chrome-devtools MCP 截图不回传、filePath 被拒；程序化检查更可靠

- 症状：`take_screenshot` 只返回 "Took a screenshot" 文本，图像不进上下文；`filePath` 落盘报 "not within any of the configured workspace roots"（连项目根目录也拒）。Browser Use 的 `nodeRepl.emitImage` 可以回传图像，但 IAB 后端 `goto()` 不支持 `file://`。
- 原因：MCP 工具的图像回传与文件写入受宿主配置限制；IAB 导航白名单只收 http/https/about:blank。
- 解法：默认用 `evaluate_script` 做程序化断言（计算样式、`getBoundingClientRect`、元素计数、`innerText.includes` 检查残留文本）；确需真实视觉时：本地 `python -m http.server` 把文件变 http:// 再用 Browser Use emitImage。断言「CSS 类不存在于输出」时用完整标签子串（如 `<details class="wx-think"`），别用会撞样式表选择器的子串。

## s14 DOM 重依赖代码的端到端自验模式：jiti 跑 TS 源码 + CORS receiver 收真实页面 DOM

- 症状：工作流允许 DOM 重依赖层跳过自动化测试，但「历史会话导出」这类 bug 恰恰藏在 DOM 抓取逻辑里，纯单测覆盖不到，等用户人工验证才发现已太晚。
- 原因：真实页面的 DOM 结构（装饰元素、组件嵌套）无法在 node 测试里复现。
- 解法：三步组合——① `node_modules/.bin/jiti script.mjs` 直接 import 项目 `src/**/*.ts`（jiti 已在依赖里），在 node 里跑真实导出管线；② 起带 `Access-Control-Allow-Origin: *` 的 node http server 接收 POST 落盘，在真实页面 `evaluate_script` 里 `fetch('http://localhost:PORT/', {method:'POST', body: JSON.stringify(数据)})` 传出 DOM 数据（text/plain 免预检）；③ node 侧用真实源码函数处理真实数据生成预览 → 本地 http 服务 → 浏览器程序化断言。

## s15 验证注入 CSS 效果先查 transition：立即读 computed style 会撞上过渡起始帧

- 症状：往页面注入样式规则（含 !important，特异性拉满甚至行内 important）后，立即 `getComputedStyle(el).backgroundColor` 读到的仍是旧值/透明，表象是「规则完全没生效、有更高优先级规则压着」，差点把修复方向带偏。
- 原因：目标元素带 `transition: background 0.3s`（DeepSeek 消息气泡原生就有），注入/改值瞬间读取正处于过渡起始帧，computed style 返回动画中间值（≈旧值）。
- 解法：验证注入 CSS 效果前先查 `getComputedStyle(el).transitionProperty` / `transitionDuration`；有 transition 就等过渡结束（duration 之后）再断言，或临时 `el.style.transition='none'` 验证后还原。本会话靠「注入后 sleep 600ms 再读」一次确认规则生效。

## s17 改主题色优先覆盖 --dsw-alias-* 变量链

- 症状：hover 态用 `--dsw-alias-button-primary-hover` 覆盖不生效，仍是写死的 DeepSeek 蓝；官方新组件把颜色变量声明在元素级（如多选复选框 `--dsl-checkbox-color`），祖先级覆盖够不着。
- 原因：官方主题有派生态与 dsw-alias 变量链两层；派生态可能是写死的 DeepSeek 蓝（hover 例：`--dsw-alias-button-primary-hover` 原生为 `--dsw-static-deepseek-450/500`），不消费 dsw-alias 链。
